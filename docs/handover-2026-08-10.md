## 3. 立即接手：C035（P0）已取消工單的 PR 仍被合併

### 現象（live 實測）

1. 建工單 → dispatch（job、PR、`ci_waiting`）
2. **執行中**由使用者把 Linear 工單改為「已取消」
3. 反覆 `run` 驅動 resume → `repair_pushed` → `requires_manual` / `lifecycle_not_completed:failed`（cause.stage=`merge`）
4. **結果：PR 已 MERGED 進 sandbox main**，工單仍「已取消」且 0 留言

期望行為（E2E 計畫 E115 定義）是：停止、Checkpoint、**關未合併 PR**、不刪 branch/worktree。實際卻把工作合併了。

### 根因（codex 已查證，並糾正了最初的推測）

- resume 對**非** `merging` 階段**其實有**重讀 Linear（`src/cli/dispatch/resume-composition.ts:1121`），但 **domain 投影把 `workStatus` 丟掉**（`src/adapters/dispatch/linear-discovery.ts:90`）→ 取消看不見。
- `merging` 階段（`resume-composition.ts:1047`）**完全不讀** Linear。
- `AutoMergeGate.enable()` 之前沒有 Linear readback（`resume-composition.ts:1791`）；`merge-gate.ts:622` 只做 GitHub pre-merge readback，沒有取消 port。
- fallback direct-squash 在 `src/cli/dispatch/status-merge-composition.ts:111`，**不在** `merge-gate.ts` 內。
- **核心成因**：`src/application/pipelines/lifecycle.ts:162` **先判斷 PR 已 merged、才判斷 canceled** → 落入「已合併但取消處置未完成」。
- E115cap 當初補的是「進入 cancellation branch **之後**」的 CAS checkpoint / requires_manual / lease release（`src/cli/dispatch/lifecycle-cancellation-adapter.ts:102`），**不是 merge 前閘門**。

### 修法（codex 裁定：選項 c，雙閘門）

1. **resume 入口**：兩種分支都要讀並**保留 `workStatus`**（含已進 `merging` 的 job）；取消時直接走 cancellation lifecycle，避免已 armed 的工作繼續。
2. **最後閘門**（真正的 merge-authorisation boundary）：`AutoMergeGate.enable()` 呼叫 GitHub 之前，**以及** direct-squash 之前（`status-merge-composition.ts:111`），各做一次權威 Linear readback。
3. **取消時**：checkpoint + 關閉尚未合併的 PR + 釋放 lease。
4. **競態處置**（readback 到 GitHub mutation 之間的窗口無法消除）：產出專用 audit incident——標 `cancellation-after-merge`、**不自動 revert**、**不標 Done**、暫停 auto-merge、留稽核留言、交人類決定；並記錄 Linear revision／讀取時間／PR SHA／mutation attempt 供稽核。

### 必備回歸測試（codex 指定 4 組）

1. `ci_waiting` 後取消 → resume 不得 enable auto-merge／direct-squash，且完成 close/checkpoint/release
2. gate readback 與 mutation 之間取消 → 兩種 mutation 都不得執行
3. 已 `merging`／已 armed auto-merge 後取消 → 下一輪 resume 必須停止
4. 取消與 GitHub 合併競態 → 必有 incident，且不自動 Done 或 revert

### 附帶：E115 的另一半也未驗

「非使用者事件不得取消」目前只有部分單元層級保護（`workflow-state` 已驗僅 `user_canceled` 可導向 canceled、canceled 不可回 completed），但**未證明** CI 失敗／lease 問題／GitHub closed／provider error 不會觸發 cancellation cleanup。需補參數化整合測試，逐一斷言：不寫 Linear canceled、不做 cancellation checkpoint/comment/close。

### 殘留現場

PR #46 已合併進 sandbox main（`24ece0a`），依 codex 裁定**不自動 revert**（內容是無害的 `lastIndex` util）。LEA-32 維持「已取消」。

## 5. 兩個已釐清的結構障礙（別重複踩）

### E104：靠工單／AC 製造 reviewer 阻擋不可行

- implementer 與 reviewer 收到**同一份 requirement snapshot**。任何寫進 AC 的缺陷，implementer 都看得到並會（正確地）先修好——實測：種了 `isOdd` 對負數回錯的 bug，implementer 讀到 AC 後主動修好還多寫了負數測試。
- 若把修復排除在宣告範圍外以避免 implementer 先修，則 fix round 會被範圍守衛擋成 `paused`（E102 defect 案例實測），走不到「修正→重審→合併」。
- reviewer 角色指令是**檔案限定**的（sandbox 的純度規則只針對 `src/sandbox.ts`、`src/failure-switch.ts`），新檔踩不到。
- **正解**：在 trusted config 的 code_reviewer 角色指令加一條 implementer 必踩、工單不會提的品質規則——但這需要走 trusted config 重新核可（含兩道人工閘門，見第 6 節）。

### fixture 類案例的成本

「需要在工單開始前就存在於 repo 的前置狀態」（種缺陷讓 base 帶病）才叫 fixture，需要一個 PR 進 sandbox main。使用者已裁定：**fixture 也要開 Linear 工單讓 agent team 自己做，不要手動放行 PR**。

而「跑到一半做一件事」（改 Linear 狀態、在 GitHub 上合併）不是 fixture，不需要動 sandbox code——E115/E116 屬此類。「自然觸發」（把工單設計成 implementer 自然會踩 lint）也不需要 fixture——E103 屬此類。

## 7. 方法論教訓（付過代價，請沿用）

1. **替換式重構必須拿舊實作當 oracle 做 old-vs-new 逐樣本對照**。C034 第一版把「舊判定式的覆蓋面」理解成「token pattern 清單」，漏掉它其實連帶擋住 authorization/cookie/URL userinfo/query key/小寫敏感鍵五類 → 9 種真憑證從擋變放行。驗收員用 45 樣本對照才抓到。**派這類 packet 時就要求此對照**。
2. **小心「測試貼合實作」**。實作者容易用「自己實作剛好能處理的形狀」寫 fixture（裸 `?token=`、無屬性 `set-cookie:`），於是綠燈只證明「實作能處理它自己能處理的」，而真實世界最常見的形狀（引號/backtick 包住的 URL、帶 `; HttpOnly` 的 Set-Cookie）全部放行。**寫完每個測試自問：這是真實 code 裡會出現的樣子嗎？**
3. **拿專案自身當語料最有力**。掃本 repo 701 檔抓到 6 個非測試檔誤判（含 scanner 自己的 doc comment）。已做成常駐測試（walk `src/**` 斷言零命中，allowlist 空）。但要記得它**只是本 repo 現況的回歸網、不具一般性**。
4. **安全判定式裡的數值門檻會擺盪**。C034 第 5~7 輪三次證明：修 FP 就開漏擋、修漏擋就開 FP。**正解是換成不會擺盪的判準**——形狀（移除門檻）或有限 allowlist（只會因遺漏而錯、方向單一、可審計）。後續維護請只動 allowlist。
5. **subagent 無法可靠等待背景 `codex exec`**。SOP：subagent 回報 pid → 主代理監看 pid → codex 結束後喚醒 subagent 收尾。
6. **會做「破壞驗證」的驗收代理不可與主代理共用工作樹**。實踩過：它的 `&& false` 暫時破壞出現在主代理的 diff，且它收尾的 `git checkout --` 洗掉了主代理的正事。派驗收時明確要求自建獨立 worktree。
7. **`git checkout --` 會連同檔案內未提交的正事一起洗掉**；還原請用 `cp` 或精確 Edit 反向改回。
8. **連「用來判 FAIL 的樣本是否貼近真實」都要檢驗**。C034 一度以合成的 Stripe 格式（全字母）為 FAIL 依據，而真實 Stripe key 含數字、本來就會被擋——這個疑慮最後由「改用 provider 前綴 allowlist」一併化解。
